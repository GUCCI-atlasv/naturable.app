# Naturable Free V2 PRD：双语自然写作编辑闭环

> 文档状态：Draft v1.0  
> 产品：Naturable.app  
> 版本范围：Free V2  
> 目标发布日期：待排期  
> 最后更新：2026-07-12  
> 负责人：Product / Design / Engineering

## 1. 文档摘要

Naturable Free V2 将从一次性的 AI 写作痕迹检查器，升级为一个可解释、隐私优先的双语自然写作编辑器，形成完整的：

**检查 → 修改 → 对比 → 复检**

产品首先把英文分析能力做深，同时支持英文和简体中文界面、输入语言识别及独立语言规则包。英文规则作为正式能力发布；中文自然度分析以 Beta 发布，并使用中文专属规则，而不是翻译英文规则。

Free V2 继续遵守以下承诺：

- 不登录也能使用。
- 不限制本地检查次数。
- 文本默认只在浏览器中处理，不上传服务器。
- 结果用于改进写作，不用于断言文本作者身份。
- 不承诺绕过 GPTZero、Turnitin 或其他 AI 检测器。

## 2. 背景与问题

### 2.1 当前产品基础

Naturable Free 当前已经支持：

- 浏览器本地规则扫描。
- AI writing tells 高亮与解释。
- Human score 和 sentence rhythm。
- 一键规则修正。
- Apply、Ignore、Undo、Copy、Clear。
- 无需注册、文本不上传。

### 2.2 当前主要问题

1. **检查之后的编辑控制不够细。** 用户主要按整类规则批量修改，无法逐个审阅命中项。
2. **修改结果缺少可见反馈。** 用户看不到明确的前后差异、修改数量和分数变化。
3. **复检不是显式流程。** 修改后虽然可以重新分析，但产品没有告诉用户哪些问题已解决、哪些仍存在、哪些是新增问题。
4. **分数容易被误解。** “Human score”可能被理解为真人创作概率，但当前实现只是启发式写作自然度指标。
5. **规则覆盖偏词汇级。** 对重复句式、段落结构、模糊论证、句子节奏等文档级问题覆盖不足。
6. **只适用于英文。** 页面、规则、句子切分和统计方式均以英文为中心。
7. **缺少持续使用能力。** 没有本地草稿、自动保存和最近编辑记录。

## 3. 产品定位

### 3.1 定位陈述

Naturable 是一个可解释、隐私优先的自然写作编辑器，帮助用户识别机械、泛化和模板化表达，并在保留原意的前提下完成自己的编辑。

### 3.2 核心价值

- **可解释：** 每个提示都说明问题、证据和修改建议。
- **可控制：** 用户决定接受哪一处修改，不强制重写全文。
- **可验证：** 每次修改都能查看差异并再次检查。
- **隐私优先：** Free 文本默认不离开浏览器。
- **语言原生：** 英文和中文使用各自的语言规则与统计方法。

### 3.3 产品措辞原则

推荐使用：

- Naturalness score / 自然度分数
- Writing patterns / 写作模式
- Strong issue / 明确问题
- Suggestion / 改进建议
- Improve clarity, rhythm, specificity and voice

禁止或避免使用：

- “真人概率”
- “100% Human”
- “保证通过检测”
- “绕过 Turnitin/GPTZero”
- 将启发式规则结果描述为作者身份判断

## 4. 目标与非目标

### 4.1 V2 目标

1. 建立完整的检查、修改、对比、复检闭环。
2. 将英文规则从关键词扫描扩展到词汇、句式、结构、节奏和论证五个层面。
3. 支持单条命中项级别的 Apply、Ignore 和 Undo。
4. 提供清晰的 Before/After Diff 和修改摘要。
5. 将 Human score 重构为可解释的 Naturalness score。
6. 支持英文和简体中文 UI、输入语言识别及语言切换。
7. 提供中文专属自然度规则 Beta。
8. 提供无需账号的本地草稿自动保存和历史恢复。
9. 建立不采集正文的基础产品分析与规则反馈机制。

### 4.2 非目标

以下内容不属于 Free V2：

- 云端 LLM 全文重写。
- 个人 Voice Profile 训练。
- 登录、云同步和多人协作。
- DOCX、PDF 等复杂文件格式导入。
- 浏览器扩展、Google Docs 或 Microsoft Word 插件。
- 抄袭检测、引用真实性检测。
- 对文本是否由 AI 生成作确定性判断。
- 对第三方 AI 检测器通过率作承诺。
- 繁体中文及除英文、简体中文外的其他语言。

## 5. 目标用户与核心场景

### 5.1 核心用户

#### A. AI 辅助写作者

使用 ChatGPT、Claude、Gemini 等生成初稿，希望减少模板化表达，但保留原意。

#### B. 非英语母语专业人士

需要检查英文邮件、报告、博客是否过度正式、重复或缺乏自然节奏。

#### C. 内容编辑与营销人员

需要快速定位批量内容中的套话、宣传腔、模糊表述和重复结构。

#### D. 中文内容创作者

希望识别中文 AI 腔、空洞总结、连接词堆叠、机械排比和意义拔高。

### 5.2 Jobs to Be Done

- 当我粘贴一段 AI 辅助生成的文本时，我想快速知道哪些具体表达显得机械，以及为什么。
- 当系统建议修改时，我想逐条决定是否接受，而不是把全文交给黑盒重写。
- 当我完成修改后，我想看到前后差异和仍未解决的问题。
- 当我使用中文时，我希望系统依据中文表达习惯分析，而不是套用英文规则。
- 当我处理敏感文本时，我希望正文不被上传或保存到服务器。

## 6. 核心用户旅程

### 6.1 首次检查

1. 用户进入 Checker。
2. 界面根据浏览器语言显示英文或简体中文，并允许手动切换。
3. 用户粘贴或输入文本。
4. 系统自动识别文本语言，用户可以覆盖选择。
5. 用户点击 Check / 检查。
6. 系统展示自然度分数、问题数量、类别分布、文本高亮和问题列表。

### 6.2 修改

1. 用户点击某一高亮或问题卡片。
2. 编辑器滚动并定位到对应文本。
3. 用户查看问题解释、修改建议和置信度。
4. 对安全规则，用户可选择 Apply / 应用。
5. 用户也可以 Ignore once / 忽略此处，或 Ignore rule / 忽略此规则。
6. 用户可以使用 Fix safe issues / 修复所有安全问题批量应用确定性修改。

### 6.3 对比

1. 发生首次修改后，Before/After 对比入口出现。
2. 用户可在 Inline、Side-by-side 两种模式查看变化；移动端只使用 Inline。
3. Diff 明确区分删除、添加和未改变内容。
4. 摘要显示修改数量、涉及规则和自然度分数变化。
5. 用户可以撤销单次修改或恢复检查前版本。

### 6.4 复检

1. 文本被修改后，主按钮变为 Recheck / 重新检查，并显示“内容已改变”。
2. 用户点击复检。
3. 系统使用当前文本重新运行全部规则。
4. 结果区显示：已解决、仍存在、新增、已忽略。
5. 用户可以继续修改，直到满意后复制结果。

## 7. 信息架构与页面结构

Checker 桌面端布局：

1. 顶部导航与语言切换。
2. 文档工具栏：输入语言、写作场景、字数、保存状态。
3. KPI 区：自然度、明确问题、建议、句子节奏。
4. 左侧：可编辑原文。
5. 右侧：当前模式下的 Highlighted 或 Diff。
6. 下方/侧栏：按类别组织的问题列表。
7. 底部操作：检查/复检、安全修复、撤销、复制、清空。

移动端使用单栏 Tabs：

- Edit / 编辑
- Issues / 问题
- Compare / 对比

## 8. 功能需求

### 8.1 文本输入与语言

#### FR-INPUT-01 文本输入

- 支持粘贴、键盘输入和纯文本 Sample。
- 单次建议上限为 10,000 英文词或 20,000 中文字符。
- 超出上限时不删除内容，提示用户缩短文本后再检查。
- 输入变化后自动保存到当前本地草稿。

#### FR-LANG-01 UI 语言

- 支持 `en` 和 `zh-CN`。
- 首次访问依据浏览器语言选择。
- 用户手动选择后持久化到本地。
- 不因自动语言判断强制跳转页面。

#### FR-LANG-02 输入语言识别

- 支持识别英文、简体中文和 Mixed/混合文本。
- 用户可手动选择 English、简体中文、Auto。
- Auto 置信度不足时提示用户确认，不阻止检查。
- Mixed 文本按文本片段运行可兼容规则；不适用的文档级指标显示为不可用。

#### FR-LANG-03 独立语言规则包

- 英文、中文规则分别加载。
- 语言规则不得依赖 UI 文案。
- 每条规则必须声明适用语言。
- 不允许通过翻译英文正则表达式生成中文规则。

### 8.2 检查引擎

#### FR-CHECK-01 规则类别

英文正式版至少覆盖：

1. Vocabulary：AI 高频词、宣传词、冗余短语。
2. Sentence patterns：否定平行句、固定开场、分词尾句、堆叠缓和语。
3. Structure：标题、列表、三段式、重复总结、段落同构。
4. Rhythm：句长过度一致、连续相同句首、标点节奏单一。
5. Evidence：模糊来源、无证据的价值判断、泛化结论。
6. Assistant artifacts：聊天寒暄、模型免责声明、占位符和残留指令。

中文 Beta 至少覆盖：

1. 套话开头与泛化背景。
2. “值得注意的是”等元话语。
3. “不仅……更/还……”等模板句式滥用。
4. “赋能、助力、打造、构建”等宣传动词堆叠。
5. 首先、其次、此外、最后等连接词机械排列。
6. 过度排比与四字词堆叠。
7. 空洞意义拔高与万能结论。
8. 模糊来源与缺失证据。
9. 段落、句首和结尾同构。
10. 助手寒暄、免责声明和残留指令。

#### FR-CHECK-02 规则数据结构

每条规则至少包含：

```js
{
  id: "en.vocabulary.ai_cliche",
  language: "en",
  category: "vocabulary",
  severity: "strong | suggestion",
  confidence: "high | medium | low",
  title: "AI cliché",
  explanation: "...",
  suggestion: "...",
  safeFix: true,
  version: 1
}
```

- `severity` 表示对写作质量的影响。
- `confidence` 表示系统对该命中的判断把握。
- 只有确定不改变语义的修改可设置 `safeFix: true`。

#### FR-CHECK-03 命中结果

每个命中项必须包含：

- 唯一 issue ID。
- rule ID。
- 起止位置。
- 命中文本。
- 严重程度与置信度。
- 可选建议文本。
- 当前状态：open、applied、ignored、resolved。

#### FR-CHECK-04 文档级规则

- 支持不对应单一文本区间的文档级问题。
- 文档级问题应展示证据，例如“8 个句子中有 6 个以 The 开头”。
- 文档级问题不得提供会改变语义的自动批量修改。

### 8.3 自然度分数

#### FR-SCORE-01 命名与说明

- 将 Human score 改为 Naturalness score / 自然度分数。
- 分数范围为 0–100。
- 明确展示：“启发式写作指标，不是 AI 作者概率。”

#### FR-SCORE-02 分数组成

分数由以下维度组成：

- Clarity / 清晰度
- Specificity / 具体性
- Rhythm / 节奏
- Structure / 结构
- Artifact-free / 无助手残留

- 各语言可使用不同权重。
- 文本少于 3 个句子时，不计算文档级节奏分。
- 修改一处低置信度建议不应导致大幅分数变化。

#### FR-SCORE-03 可解释性

- 用户可展开查看扣分来源。
- 展示维度分，不展示伪精确的“AI probability”。
- 分数变化必须能够关联到已解决或新增的问题。

### 8.4 修改操作

#### FR-EDIT-01 单处应用

- 用户可以对单个命中项应用安全修改。
- 应用后只修改对应区间，不修改同规则的其他命中。
- 修改后该问题标记为 Applied，等待复检确认是否 Resolved。

#### FR-EDIT-02 忽略

- Ignore once 只忽略当前命中项。
- Ignore rule 忽略当前草稿中的该规则。
- 忽略状态保存在草稿中，不跨草稿默认继承。
- 用户可以在 Ignored 列表中恢复问题。

#### FR-EDIT-03 安全批量修复

- “Fix safe issues”只应用 `safeFix: true` 且 confidence 为 high 的规则。
- 执行前显示预计修改数量。
- 整次批量操作可一步撤销。
- 不允许对语义型、结构型问题执行自动批量重写。

#### FR-EDIT-04 Undo/Redo

- 支持至少 50 步 Undo/Redo。
- 手动输入、单处应用和批量修复均进入历史栈。
- “恢复检查前版本”作为独立操作提供。

### 8.5 对比

#### FR-DIFF-01 基准版本

- 每次首次 Check 时保存 baseline。
- Recheck 不覆盖当前 baseline，除非用户选择“设为新基准”。
- 清空草稿后删除对应 baseline。

#### FR-DIFF-02 对比视图

- 桌面端支持 Inline 和 Side-by-side。
- 移动端支持 Inline。
- 删除内容用删除样式，新增内容用新增样式。
- 支持按修改跳转上一处/下一处。
- Diff 必须以词为主、字符为辅，避免整段显示为全部改变。

#### FR-DIFF-03 修改摘要

摘要至少显示：

- 修改总数。
- 添加/删除的词数或字符数。
- 涉及的规则类别。
- 自然度分数前后变化。
- 已解决、仍存在和新增问题数量。

### 8.6 复检

#### FR-RECHECK-01 状态提示

- 检查后文本发生变化时显示 Dirty 状态。
- 主 CTA 从 Check 变为 Recheck。
- 未复检前不得把 Applied 等同于 Resolved。

#### FR-RECHECK-02 结果分类

复检后按稳定 rule ID 和文本位置匹配问题，分类为：

- Resolved：旧问题已消失。
- Remaining：旧问题仍存在。
- New：修改后新出现的问题。
- Ignored：用户明确忽略的问题。

#### FR-RECHECK-03 复检摘要

- 首屏显示“已解决 X，仍有 Y，新增 Z”。
- 默认优先展示 Remaining 和 New。
- 用户可展开查看 Resolved。

### 8.7 写作场景

#### FR-PURPOSE-01 场景选择

Free 支持：

- General
- Email
- Blog
- Academic
- Marketing
- Social
- Technical

- 场景只调整规则权重、阈值和解释，不调用云端模型。
- 切换场景后提示用户重新检查。
- Academic 场景不得把正式词汇本身视为强问题。

### 8.8 本地草稿

#### FR-DRAFT-01 自动保存

- 使用 IndexedDB；不可用时降级到 localStorage。
- 输入停止 500–1,000ms 后保存。
- 显示 Saved locally / 已保存到本地。
- 不将正文上传到 analytics 或服务器。

#### FR-DRAFT-02 草稿历史

- 最多保存最近 10 个草稿。
- 支持命名、恢复和删除。
- 超出数量时删除最旧且未命名的草稿。
- 提供“删除所有本地数据”。

#### FR-DRAFT-03 无痕/受限环境

- 存储不可用时产品仍可完成检查闭环。
- 明确提示该会话不会被恢复。

### 8.9 复制与清空

#### FR-OUTPUT-01 复制

- 默认复制当前编辑文本，而不是高亮 HTML。
- 成功后显示非阻塞反馈。
- 支持 Copy changes summary，输出不包含正文。

#### FR-OUTPUT-02 清空

- 有未保存或未复制修改时需要二次确认。
- 清空当前草稿时同时清除 baseline、问题和 undo 栈。

## 9. 双语与本地化规范

### 9.1 URL 与 SEO

推荐使用目录结构：

```text
/en/
/en/app/
/zh-cn/
/zh-cn/app/
```

- 每个页面设置正确的 `lang`。
- 配置 `hreflang="en"`、`hreflang="zh-CN"` 和 `x-default`。
- canonical 指向同语言正式 URL。
- Sitemap 包含两种语言页面。

### 9.2 文案

- UI 文案使用 locale key，不写死在 HTML 或规则引擎中。
- 规则标题、解释和建议支持本地化。
- 英文规则可以在中文 UI 下用中文解释，但命中文本和修复仍按英文规则处理。
- “中文 Beta”必须在输入语言和结果区清晰展示。

### 9.3 中文技术处理

- 中文句子主要依据 `。！？；` 切分，同时处理引号结尾。
- 字数使用字符数，并可内部使用分词 token；UI 不将空格作为中文词数依据。
- 节奏指标结合句子字符长度、分句数量和标点分布。
- 中英文混排不得破坏原始空格、标点和专有名词。

## 10. 隐私、安全与数据

### 10.1 Free 数据边界

- 正文、baseline、diff 和草稿只存储在用户浏览器。
- 不通过网络请求、日志、错误上报或 analytics 发送正文。
- 错误日志必须过滤输入文本、命中文本和 diff 内容。

### 10.2 Analytics 允许采集

仅允许采集不包含正文的事件：

- `check_started`
- `check_completed`
- `issue_applied`
- `issue_ignored_once`
- `rule_ignored`
- `safe_fix_all`
- `compare_opened`
- `recheck_completed`
- `copy_completed`
- `draft_restored`
- `language_selected`
- `rule_feedback_submitted`

允许的事件属性：

- UI language
- input language
- writing purpose
- rule ID
- category
- severity
- issue count bucket
- text length bucket
- processing time bucket

禁止的事件属性：

- 原文或修改后正文
- 命中片段
- Diff 内容
- 草稿标题
- 可还原文本的 hash

### 10.3 规则反馈

- 用户可以标记 Helpful / Not helpful / False positive。
- 默认只上传 rule ID、语言、场景和反馈类型。
- 如未来允许提交文本案例，必须单独明确授权，且不属于本版本。

## 11. 非功能需求

### 11.1 性能

- 2,000 英文词或 4,000 中文字符的检查，目标设备 P75 小于 300ms。
- 10,000 英文词或 20,000 中文字符的检查小于 1.5s。
- 输入过程中不实时运行完整扫描，避免键入卡顿。
- 首次可交互时间不得因中文规则包明显下降；语言包按需加载。

### 11.2 可访问性

- 满足 WCAG 2.2 AA 基础要求。
- 问题严重程度不能只通过红/黄色区分。
- 所有操作支持键盘访问。
- 高亮可通过 Tab 聚焦，并由屏幕阅读器读出问题标题和建议。
- Diff 的添加和删除需要文本标签或可访问描述。
- 移动端触控目标不小于 44×44px。

### 11.3 浏览器

支持最近两个主要版本：

- Chrome
- Edge
- Safari
- Firefox

## 12. 成功指标

### 12.1 北极星指标

**完成一次有效编辑闭环的检查会话比例。**

有效闭环定义：

```text
Check → 至少一次 Apply/手动修改 → Compare 或 Recheck → Copy
```

### 12.2 核心指标

- Check → 任意修改转化率 ≥ 45%。
- 修改用户中的 Compare 打开率 ≥ 35%。
- 修改用户中的 Recheck 完成率 ≥ 50%。
- Recheck 后 Copy 完成率 ≥ 40%。
- Safe Fix 的 Undo 率 ≤ 8%。
- 英文 Strong 规则人工 precision ≥ 90%。
- 英文 Suggestion 规则人工 precision ≥ 75%。
- 中文 Beta Strong 规则人工 precision ≥ 85%。
- 2,000 词检查 P75 < 300ms。
- 7 日回访率相对 V1 提升 30%。

### 12.3 护栏指标

- 页面崩溃率不高于 V1。
- 不发生正文进入服务端日志或 analytics 的隐私事故。
- 自动修改不得破坏 URL、Markdown 链接、代码片段和专有名词。
- Strong 规则误报率不得因规则数量增加而持续上升。

## 13. 测试与质量门槛

### 13.1 测试集

英文正式版发布前至少准备：

- 300 段人类写作。
- 300 段主流模型原始输出。
- 200 段人机混合编辑文本。
- 覆盖 Email、Blog、Academic、Marketing、Social、Technical。

中文 Beta 发布前至少准备：

- 200 段人类写作。
- 200 段主流模型原始输出。
- 100 段人机混合编辑文本。
- 至少一名中文母语编辑审核规则和建议。

所有测试语料必须确认版权和数据使用许可，不保存真实用户正文。

### 13.2 自动化测试

- 每条规则至少一个 positive 和 negative fixture。
- 测试重叠命中和区间稳定性。
- 测试单处应用不会修改其他命中。
- 测试批量修复的整组 Undo。
- 测试 Diff 对中英文、标点、换行和 emoji 的处理。
- 测试复检的 Resolved/Remaining/New 分类。
- 测试 Markdown、URL、邮箱、代码块不被误改。
- 测试浏览器存储失败时的降级路径。

### 13.3 人工验收

- 英文由熟练英文编辑抽查。
- 中文由中文母语编辑抽查。
- 对 Academic 和非母语英文文本单独评估误报。
- 不以第三方 Detector 分数作为发布门槛。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 规则数量增加导致误报 | 用户不信任结果 | 区分 severity/confidence；建立语料集和单规则 precision |
| 自动修复改变原意 | 高风险体验问题 | 仅 high confidence + safeFix 可批量处理；完整 Undo/Diff |
| 分数被理解为 AI 概率 | 品牌和伦理风险 | 改名 Naturalness score；在结果旁持续解释 |
| 中文只是英文逻辑翻译 | 中文结果质量差 | 独立中文规则包、统计方式和母语审核 |
| Diff 在长文本中性能差 | 阻塞编辑闭环 | Web Worker、增量计算、限制展示范围 |
| 本地历史被误解为云保存 | 数据丢失投诉 | 明确“仅保存在此浏览器”；提供导出提醒 |
| Analytics 意外携带文本 | 隐私事故 | 事件 schema 白名单、正文过滤测试、网络请求审计 |
| 多语言同时开发拖慢英文质量 | 延期 | 英文正式版与中文 Beta 使用不同发布门槛 |

## 16. 依赖与技术建议

- 将当前单文件规则引擎拆为 core、language rules、scoring、diff、storage、locales。
- 检查和文档级统计建议运行在 Web Worker，避免阻塞编辑器。
- 规则使用稳定 ID，不以展示标题作为数据主键。
- 使用纯函数生成 issues，方便测试、复检匹配和版本回放。
- 每次检查记录本地 engine version，便于规则升级后解释结果变化。
- Diff 库必须支持 Unicode 和中文字符，不得只按空格分词。

建议目录：

```text
site/assets/app/
├── core/
│   ├── analyzer.js
│   ├── scoring.js
│   ├── issue-matcher.js
│   └── diff.js
├── rules/
│   ├── en.js
│   └── zh-cn.js
├── locales/
│   ├── en.json
│   └── zh-cn.json
├── storage/
│   └── drafts.js
└── worker/
    └── analyzer-worker.js
```

## 17. 发布验收标准

Free V2 只有在以下条件全部满足后才可全量发布：

- 用户可完成 Check → Apply/Edit → Compare → Recheck → Copy。
- 单处 Apply 不影响同规则其他命中。
- 批量安全修复可一步撤销。
- Diff 在英文、中文和混合文本中正确显示。
- Recheck 正确区分 Resolved、Remaining、New、Ignored。
- 英文规则达到正式版 precision 门槛。
- 中文 UI 完整，中文规则达到 Beta precision 门槛。
- 输入语言可自动识别且可手动覆盖。
- 所有正文处理和草稿保存在浏览器本地。
- 网络审计确认正文、命中片段和 diff 未离开浏览器。
- 键盘、屏幕阅读器和移动端核心流程可用。
- 性能达到 P75 指标。
- 页面和结果不包含“真人概率”或“保证绕过检测”的表述。

## 18. 待确认事项

以下事项不阻塞本 PRD 进入设计和技术评审，但需在开发排期前确认：

1. 中文 Beta 是与英文 V2 同日发布，还是晚一个迭代发布。
2. 10,000 英文词 / 20,000 中文字符上限是否符合目标设备性能。
3. 是否在 V2 首发包含 Side-by-side Diff，或先上线 Inline Diff。
4. 本地草稿是否默认开启，还是首次使用时提示用户选择。
5. 中文首批规则的最终清单和母语编辑审核负责人。
6. Analytics 使用 Cloudflare Web Analytics、Workers Analytics Engine 或完全自建事件端点。
